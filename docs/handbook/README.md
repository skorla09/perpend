# PERPEND HANDBOOK

> **Establish the reference.**
> **Build with intention.**
> **Leave the workshop better than you found it.**

---

Welcome to the **Perpend Handbook**.

This handbook is the engineering companion to Perpend.

While the source code demonstrates **how** Perpend is built, this handbook explains **why** it is built this way. It preserves the philosophy, architectural decisions, engineering principles, and lessons that shape the project.

Its purpose is not simply to document the project.

Its purpose is to preserve understanding.

---

# PURPOSE

The handbook exists to:

- Explain the reasoning behind architectural and engineering decisions.
- Document the principles that guide the project's evolution.
- Provide a long-term reference for contributors and future maintainers.
- Preserve the knowledge gained while building Perpend.
- Serve as a learning resource for developers interested in software engineering, architecture, and thoughtful project design.

---

# WHO THIS HANDBOOK IS FOR

This handbook is intended for anyone who wants to understand the engineering behind Perpend.

Whether you are:

- exploring the architecture of a modern Neovim configuration,
- contributing to Perpend,
- organizing your own editor configuration,
- or simply interested in software engineering,

our hope is that these documents encourage you to think more deliberately about the systems you build.

Perpend is not intended to teach only _what_ decisions were made.

It aims to explain _why_ they were made.

---

# HOW TO READ THIS HANDBOOK

Although every chapter can be read independently, the handbook is organized as a progressive journey.

The recommended reading order is:

1. **Philosophy** — Why Perpend exists.
2. **Vision** — Where the project is headed.
3. **Engineering Principles** — The values that guide every decision.
4. **Architecture** — How the project is organized.
5. **Roadmap** — Current milestones and future direction.
6. **Style Guide** — Coding and writing conventions.
7. **Folder Structure** — Repository organization and responsibilities.
8. **Plugin Guidelines** — Standards for evaluating and integrating plugins.
9. **Milestones** — Lessons learned throughout the project's evolution.
10. **Architecture Decision Records (ADRs)** — Significant engineering decisions and their rationale.
11. **Research Notes** — Investigations and evaluations conducted before adopting new technologies.
12. **Agent Guide** — How agents and contributors operate within the repository.

Each chapter builds upon the previous one.

Together they tell the story of how Perpend is engineered.

---

# A LIVING HANDBOOK

The Perpend Handbook evolves alongside the project.

When the architecture changes, the handbook should reflect those changes.

When an important engineering decision is made, it should be documented.

When a lesson is learned, it should be preserved.

Documentation records information.

The handbook preserves understanding.

As Perpend evolves, this handbook should continue to grow—not only as documentation, but as a record of the engineering discipline that shaped it.
