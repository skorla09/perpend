# PHILOSOPHY

`Build software that teaches`

Every project begins with a question

Perpend began with this one:

`How difficult would it be to build a Neovim configuration that feels like a professional code editor?`

As the project evolved, another question emerged

An important one

`Can a Neovim configuration teach software engineering by the way it is built?`

That question became the foundation of Perpend

## WHY PERPEND EXISTS

There are already many excellent Neovim configurations.

Many provide outstanding defaults, powerful workflows, and impressive collections of plugins

Perpend does not exist to compete with them

It exists to demonstrate a different idea

That software can be engineered in a way that is intentionally understandable

Every architecture decision, every directory, every plugin integration, and every document should help answer not only what the project does, but why it was designed that way

Understanding is treated as a feature

## BEYOND A NEOVIM configuration

Although Perpend is built for Neovim, its purpose extends beyond the editor configuration

The project is an exercise in software engineering

It is a place to explore ideas such as:

- thoughtful architecture
- clear separation of responsibilities
- intentional documentation
- maintainable project organization
- and long-term thinking

The editor is the medium

Engineering is the objective

## OUR MEASURE OF SUCCESS

Success is not measured by the number of plugins

It is not measured by the number of features

It is not measured by popularity

Instead, Perpend succeeds when another developer can open the repository and think:

`I understand why this project is organized this way`

If the project encourages someone to write cleaner code, organize a project more thoughtfully, or approach software architecture with greater intention, then it has achieved its purpose

## A PROMISE

Perpend is built deliberately

Every feature should have a reason to exist

Every dependency should justify its place

Every architectural decision should be explainable

When clarity and convenience conflict, clarity will win

The goal is not to build the most impressive configuration

The goal is to build one that remains understandable for years to come

```text
Architecture begins long before code is written,

It begins with the way we choose to think
```
